Vercel AI SDK 6：前端开发者构建 Agent 应用的新基线

Vercel AI SDKNext.jsAI应用

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

AI 应用不是一个聊天框。生产环境里的前端要处理流式输出、工具调用、审批、失败、取消、重试、结构化结果和观测指标。如果这些状态没有被设计成清晰流程，模型越强，产品越不可控。

这篇从前端状态机角度重新梳理 AI 应用：什么时候让模型回答，什么时候调用工具，什么时候必须让用户确认，工具失败后如何回退。

GitHub 源码观察

这次重写特意参考了 GitHub 上的真实仓库。它们的价值不只是提供链接，而是能把文章从“概念说明”拉回到“工程现场”：目录怎么分、规则怎么写、测试怎么放、工具权限怎么收。

  • vercel/ai：AI SDK 仓库把核心包、UI、examples、tools、skills 放在一起，适合说明 AI 应用要同时处理模型调用、界面状态、工具调用和 Agent 规则。
  • vercel-labs/mcp-to-ai-sdk：把 MCP 工具转成 AI SDK stub 的思路很值得借鉴：不要把远程工具裸接进产品，先收窄参数、权限和上下文。

核心痛点

  • 只做聊天框，没有把工具调用、审批、失败、取消做成状态机。
  • 模型输出自由文本，前端靠字符串解析驱动 UI。
  • 工具直接执行写操作，用户不知道影响范围。
  • 没有观测指标，线上慢在哪里、失败在哪里都看不清。

详细解决方案：把 AI 应用做成可控状态机

AI 应用的前端难点不是消息列表，而是状态。一个成熟的 AI 应用至少要处理：生成中、等待工具、等待审批、工具执行中、工具失败、取消、重试、完成。

状态机设计

idle -> streaming -> tool_pending -> approval_required
approval_required -> tool_running -> completed
tool_running -> tool_failed -> retry | cancel
streaming -> cancelled

工具审批 UI

涉及写操作时，必须展示工具名称、参数摘要、影响范围和取消入口。例如“更新用户资料”要显示会修改哪些字段；“创建工单”要显示标题、接收人和内容摘要。

结构化输出

让模型输出 JSON 或 schema 化数据，前端用结构驱动 UI。不要从 Markdown 里找关键词来决定按钮和状态。

实战案例：客服助手的工具审批

用户要求“帮我修改收货地址”时，前端不能直接让模型调用写接口。先让模型输出结构化意图，再展示影响字段和确认按钮。

只有用户确认后才执行工具。工具失败时展示可重试状态，而不是继续让模型编一个看似成功的回复。

进一步落地：把工具调用设计成用户看得懂的流程

AI 应用里最容易被忽略的是“用户不知道 AI 正在做什么”。前端应该把工具调用拆成可见步骤：识别意图、准备工具、展示影响范围、等待确认、执行、展示结果、失败可重试。

状态和 UI 对照表

状态UI 表现
streaming显示生成中，可取消
tool_pending展示将调用的工具和参数摘要
approval_required显示确认 / 取消按钮
tool_running显示进度和不可重复提交
tool_failed显示失败原因、重试和回退
completed显示结构化结果和后续操作

结构化输出 Prompt

你必须返回 JSON：
{
  "intent": "update_profile" | "query" | "create_ticket",
  "summary": "给用户看的摘要",
  "requiresApproval": true,
  "risk": "low" | "medium" | "high",
  "fieldsChanged": [],
  "nextActions": []
}
如果风险不确定，requiresApproval 必须为 true。

这样前端就不需要从一段自然语言里猜按钮和状态，UI 会稳定很多。

前端 AI 应用的核心不是聊天框

很多 AI 应用第一版都是聊天 UI，但真正复杂的是状态管理：模型正在思考、正在调用工具、等待用户确认、工具失败、重试、取消、恢复历史。这些状态如果只靠自然语言渲染，会很快变成不可维护的字符串解析。AI SDK 的价值在于把模型、工具、流式输出和 UI 状态放进统一的 TypeScript 结构里。

工具调用的 UI 设计

工具调用不要只显示“AI 正在处理”。更好的方式是把每个步骤展示成可理解的状态：读取订单、检查库存、生成方案、等待确认、执行修改。涉及写操作时，前端应该明确展示工具名称、影响范围和确认按钮。用户确认后再调用服务端工具，而不是让模型在后台直接写数据。

结构化输出示例

{
  "intent": "update_profile",
  "summary": "准备更新用户昵称和头像",
  "requiresApproval": true,
  "fields": ["nickname", "avatar"],
  "nextActions": ["confirm", "edit", "cancel"]
}

前端拿到这样的结构，就可以稳定渲染按钮、表单和风险提示。相比让模型输出一段 Markdown，再从里面找“确认”两个字，结构化输出更容易测试，也更适合国际化和埋点。

调试和观测

AI 产品上线后，问题经常不是“模型坏了”，而是某一步工具返回慢、上下文太长、提示词缺少边界、用户输入触发了异常路径。开发期要记录每一步耗时、token、工具参数和错误。用户界面也要提供取消和重试，不要让一次失败把整个会话锁死。

前端安全边界

密钥只放服务端。浏览器端只拿到会话状态和可展示数据。工具返回也要分层：给模型的摘要尽量少，给 UI 的数据按权限过滤。这样既能减少上下文污染，也能降低敏感数据被模型复述的风险。

AI 应用文章应该讲清楚状态机

很多 AI 应用教程只展示流式聊天，很容易让人误以为前端只要渲染消息列表。生产环境完全不是这样。真正复杂的是状态机：模型生成中、工具调用中、等待审批、工具失败、用户取消、重试、上下文过长、权限不足。文章要把这些状态讲清楚，读者才知道怎么写一个能上线的 AI 应用。

前端状态设计

idle：等待输入。
streaming：模型正在输出。
tool_pending：工具准备执行，展示影响范围。
approval_required：需要用户确认。
tool_running：工具执行中。
tool_failed：可重试或回退。
completed：任务完成，展示结构化结果。

这些状态最好不要散落在组件里，而是集中在 hook 或状态机中。否则当工具数量增加时，按钮禁用、加载文案、错误提示会变得混乱。

工具审批 UI

涉及写操作时，前端必须展示工具名称、参数摘要、影响范围和取消入口。例如“更新用户资料”要展示将修改哪些字段；“创建工单”要展示标题、描述和接收人。不要让模型一句“我将帮你处理”就直接执行。

调试指标

  • 首 token 时间和完整响应时间。
  • 每次工具调用耗时和失败率。
  • 用户取消率和重试率。
  • 审批通过率，判断工具是否设计得过于激进。
  • 结构化输出解析失败率。

前端工程师在 AI 应用里的价值，会越来越体现在“把不确定模型行为变成可理解、可取消、可恢复的产品体验”。
