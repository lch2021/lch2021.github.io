Figma MCP 与 Figma Make：前端如何把设计上下文交给 AI

2026年4月29日 下午 2916 字 6 分钟
Figma设计系统MCP

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

设计转代码的失败，通常不是因为 AI 不会写 CSS，而是因为它只看到了截图，没有理解设计系统。一个按钮在 Figma 里不只是蓝色矩形，它可能对应组件库里的 Button、token、状态、可访问性和响应式规则。

这篇强调一个前置动作：先建立设计元素到代码组件的映射，再让 AI 写代码。没有映射表，就不要进入实现阶段。

核心痛点

  • 截图转代码只能看像不像，无法理解设计系统语义。
  • Agent 不知道组件映射，重复造 Button、Card、Modal。
  • 只实现成功态，漏掉空态、错误态、长文本和移动端。
  • 设计稿和代码 token 没对齐，后续维护成本高。

详细解决方案：先做映射表，再写代码

设计到代码的核心不是让 AI 看截图，而是让它理解组件和 token。实现前必须输出映射表：Figma 元素对应哪个代码组件、使用哪些 token、哪些状态缺失、哪些地方需要确认。

映射表：
Figma Button -> Button variant="primary"
Info Card -> Card + Description
User Avatar -> Avatar with fallback
Filter Panel -> Drawer on mobile
Empty State -> EmptyState + RetryButton

验收标准

  • 375px、768px、1440px 三个视口无横向滚动。
  • 长文案、缺图、接口失败、无权限都有状态。
  • 颜色、间距、字号尽量使用 token。
  • 新增 UI 必须有 story 或截图验证。

实战案例：设计稿落地为响应式设置页

让 Agent 先读 Figma frame 并输出映射表：哪些是现有组件，哪些 token 可复用，哪些状态缺失。确认后再写代码。

实现完成后补 375px 和 1440px 截图，长文本和错误态单独验证。设计还原不只看截图相似度，还要看组件语义。

进一步落地：设计实现前必须先做组件映射

如果 Agent 直接根据截图写代码，很容易生成一次性样式。更好的方式是先让它输出设计到代码的映射表，确认哪些元素可以复用组件库，哪些需要新增，哪些设计信息缺失。

映射表模板

Figma 元素 | 代码组件 | Token | 状态 | 风险
Primary Button | Button | color.primary | loading/disabled | props 待确认
Info Card | Card | spacing.md | normal/error | 移动端换行
User Avatar | Avatar | size.40 | fallback | 缺默认头像
Filter Drawer | Drawer | zIndex.drawer | open/close | 焦点回收

验收清单

  • 设计 token 是否被使用，而不是硬编码颜色和间距。
  • 长文本、缺图、空态、错误态是否都有处理。
  • 移动端是否从横向布局切换到纵向或抽屉。
  • 新增组件是否补 story，而不是只在页面里可见。

从“看图写代码”到“读设计系统”

截图只能告诉 Agent 视觉结果，不能告诉它组件语义。比如一个按钮看起来是蓝色矩形，但它可能对应 Design System 里的 Primary Button，包含 loading、disabled、icon、size、a11y label 等一组行为。如果 Agent 只看截图，就很容易写出一个只在当前页面好看的临时实现。

Figma MCP 的正确打开方式

使用 Figma MCP 时，提示词要要求 Agent 先读取 frame 和组件信息，再输出实现计划。计划里应该列出：复用哪些代码组件，哪些设计 token 对应颜色和间距，哪些地方需要响应式处理，哪些设计信息缺失。这样你能在写代码前发现偏差。

请先读取 Figma frame，不要直接写代码。
输出：
1. 识别出的页面区块。
2. 可复用的项目组件。
3. 对应的 token 或变量。
4. 缺失信息和需要确认的问题。
确认后再开始实现。

Code Connect 的意义

如果团队维护了 Code Connect，Agent 就能把设计组件和代码组件对应起来。例如 Figma 里的 Alert 组件对应项目里的 AlertMessage，Button 的 variant 对应代码里的 type 或 variant。这能显著减少错误 props 和重复造组件。

Figma Make 适合放在哪个阶段

Figma Make 更适合产品早期探索：做一个交互原型、验证布局、快速讨论流程。进入生产代码阶段，要回到组件库、代码规范、测试和可访问性。不要把原型代码直接合并到项目，因为原型通常没有处理权限、接口异常、国际化、性能和状态边界。

验收方式

设计还原不能只靠肉眼。建议把目标页面做成 story 或独立路由，用 Playwright 截图 375px 和 1440px；再检查键盘焦点、表单错误、图片比例和长文本换行。AI 负责第一版实现，人负责判断设计意图是否被正确表达。

设计到代码文章不能只讲还原度

别人写得好的设计转代码文章，通常会把“还原度”拆成多个维度：视觉、组件语义、响应式、状态、可访问性、设计 token。只看像不像截图，很容易忽略生产代码最重要的部分。例如设计稿里一个输入框看起来很简单，但真实组件可能包含错误提示、帮助文案、禁用态、字符限制和 aria 描述。

给 Agent 的设计读取清单

  • 页面分成哪些区域，每个区域对应哪个业务组件。
  • 哪些元素来自设计系统，哪些是页面特有样式。
  • 颜色、间距、圆角、阴影是否能映射到 token。
  • 移动端布局如何变化，是否有折叠、换行或滚动。
  • 缺失的状态有哪些，例如空态、错误态、加载态。

实现前先让 AI 输出映射表

Figma 元素        代码组件            说明
Primary Button   Button              使用 variant="primary"
Info Card        Card + Description   复用 Card，不新增外层样式
User Avatar      Avatar              需要 fallback 文案
Filter Panel     Drawer              移动端改为底部弹层

映射表能提前暴露问题：如果 Agent 找不到对应组件，它应该停下来问，而不是自己写一个“看起来像”的新组件。

验收不只截图

截图对比只能发现视觉问题，不能发现键盘操作、屏幕阅读器、接口失败和长文本换行。建议设计稿实现完成后，至少补一个 story、两个 viewport 截图、一个长文本用例和一个错误态用例。这样 AI 生成的页面才真正进入工程体系。
