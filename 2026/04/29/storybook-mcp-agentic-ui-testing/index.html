Storybook MCP：让 AI 前端代码先过组件和可访问性测试

2026年4月29日 下午 2925 字 7 分钟
Storybook组件测试可访问性

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

AI 写 UI 最大的问题是“看起来对”。它可能猜错组件 props，只实现成功态，漏掉 a11y 和长文本。Storybook MCP 的价值是让 Agent 先读组件文档、生成 stories、运行交互测试和可访问性检查，而不是凭经验硬写。

这篇用状态矩阵来约束 UI 生成：先查组件，后列状态，再写 story，最后用测试失败驱动修复。

核心痛点

  • AI 写 UI 时猜组件 props，导致代码能编译但不符合组件库。
  • 组件只有成功态，测试覆盖不了真实边界。
  • a11y 问题到 QA 或线上才暴露。
  • 快照更新没有说明，视觉回归被悄悄吞掉。

详细解决方案：用状态矩阵约束 AI 写 UI

让 Agent 写 UI 前，先让它查 Storybook MCP，确认组件 props 和已有 stories。然后要求它列状态矩阵，再写代码。状态矩阵能把“看起来正常”的成功态，扩展成真实业务会遇到的边界。

维度状态
数据loading / empty / partial / full / error
权限guest / user / admin / forbidden
交互default / focus / disabled / submitting
内容短文本 / 长文本 / 缺图 / 极端数字
视口375px / 768px / 1440px

失败处理原则

测试失败时，不允许直接删断言或更新快照。必须先解释失败原因，再改实现，最后重新运行测试。

实战案例：BillingSummary 状态矩阵

组件原来只有 normal story，AI 改动时经常漏 loading 和 error。先补状态矩阵，再让 Agent 写 stories。

新增 loading、empty、error、longText 四个 story，并跑 a11y 检查。以后页面复用该组件时，Agent 可以直接查文档而不是猜 props。

进一步落地：先状态矩阵，后组件实现

AI 写 UI 之前，先要求它列状态矩阵。状态矩阵不是文档装饰，而是约束实现范围。没有状态矩阵，Agent 通常只实现 normal 状态。

状态矩阵模板

组件：BillingSummary
数据：loading / empty / full / error
权限：normal / readonly / forbidden
交互：default / focus / disabled / submitting
内容：短文本 / 长文本 / 价格极大 / 缺少字段
视口：375px / 768px / 1440px

Story 生成要求

每个关键状态都应该有 story。Agent 写完 story 后，先跑组件测试和 a11y 检查。失败时不允许删断言，必须先解释失败原因，再修改实现。

PR 验收

UI PR 至少说明新增了哪些 story、覆盖哪些状态、是否运行 a11y、移动端是否检查。没有这些信息，代码看起来再漂亮也不完整。

为什么 Storybook 是 AI 写 UI 的约束层

前端 Agent 最容易犯的错，是不知道项目里已有组件的真实 API。它可能把 Button 的 type 写成 variant，把 Modal 的 open 写成 visible，或者完全绕过组件库写一套 class。Storybook MCP 的价值在于让 Agent 先查组件文档和 stories，再写代码。

把状态补全

业务组件不要只写成功态。至少准备 loading、empty、error、normal 四个 story。复杂一点的表单还要补 disabled、validation error、submit pending。这样 Agent 做后续改动时，有明确的视觉和交互样本可以参考。

stories:
- Normal：有完整数据。
- Loading：骨架屏或 loading 状态。
- Empty：无数据但操作入口可见。
- Error：接口失败，可重试。
- LongText：标题和描述超长，验证换行。

让 Agent 自己跑组件测试

如果 Storybook MCP 暴露了测试工具，就可以要求 Agent 在提交前运行组件测试和可访问性检查。失败时不要让它删除断言，而是让它先解释失败原因，再做最小改动。a11y 问题尤其适合这样处理，因为很多错误都有明确规则：缺少 label、焦点不可达、颜色对比不足、aria 属性不匹配。

团队规则

把“使用组件前先查 Storybook MCP”写进 AGENTS.md 或 Rules。再把“新增 UI 必须新增或更新 story”写进 PR 模板。这样 AI 生成的代码不只是能运行，还能进入团队现有的组件文档和测试体系。

长期收益

当 Storybook 足够完整时，Agent 能做的事情会明显变多：按现有组件拼页面、补边界状态、修 a11y、更新交互测试、生成使用文档。这个收益不是一次性的，它会随着组件文档质量变好而持续放大。

组件测试文章要从状态矩阵开始

高质量前端测试文章不会只说“要写测试”，而是先列状态矩阵。Storybook MCP 的价值也在这里：它让 Agent 能看到组件在各种状态下应该是什么样，而不是只根据当前页面猜。

状态矩阵示例

数据状态：loading / empty / partial / full / error
权限状态：guest / normal / admin / forbidden
交互状态：default / hover / focus / disabled / submitting
内容状态：short text / long text / missing image / extreme number
视口状态：375px / 768px / 1440px

给组件补 story 时，至少覆盖最容易出错的交叉点。比如“移动端 + 长文本 + 错误态”往往比普通成功态更容易暴露问题。

让 AI 按测试失败修正

不要让 Agent 一次写完组件、story、测试并宣布成功。更稳的流程是：先写 story，再运行 a11y 和交互测试，失败后让它根据错误修正。这样测试是约束，不是装饰。

PR 模板可以这样写

UI 改动是否更新 story：是 / 否
覆盖状态：loading、empty、error、success
是否运行组件测试：是 / 否
是否检查移动端：375px / 768px / 1440px
是否存在 a11y 风险：说明

当这些字段成为团队习惯后，AI 生成 UI 的质量会更稳定。Agent 不再只是写页面，而是在你的组件系统里补齐文档和测试。
