把 AI 能力技能化：AGENTS.md、Rules、Instructions 的前端写法

2026年4月29日 下午 2508 字 6 分钟
技能AGENTS.md团队规范

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

AI 反复犯同一个错，通常不是模型问题，而是团队没有把约定写成可执行规则。老成员知道不能直接写 button、知道要复用 EmptyState、知道移动端不能横向滚动，但 Agent 不知道。

这篇讲如何把 Review 返工点变成 AGENTS.md、Rules 和技能卡，让 AI 每次开工前先读规则，而不是每次都靠你口头纠正。

核心痛点

  • 团队约定只在老成员脑子里，AI 每次都猜错。
  • 规则文档写成口号，无法验证也无法执行。
  • 不同工具各写一套提示词，维护成本高。
  • Review 中反复指出同一类问题，却没有沉淀成规则。

详细解决方案：把团队经验写成可执行接口

AGENTS.md、Rules、Instructions 的目标不是写漂亮文档，而是把团队约定变成 Agent 能执行的接口。接口必须短、硬、可验证。

规则模板

# 目录边界
src/components 不引入业务 API。
src/pages 可以组合业务逻辑，但不复制通用 UI。
src/api 只封装请求，不处理页面状态。

# UI 规则
新增业务组件必须覆盖 loading/empty/error/success。
移动端 375px 不允许横向滚动。
按钮、弹窗、空态必须复用组件库。

迭代方式

每次 AI PR 返工后，把问题归类：上下文缺失、范围过大、组件 API 猜错、测试不足、安全风险。某类问题出现两次，就补进规则。

实战案例：把 Review 返工变成规则

连续三次 AI PR 都新增了原生 button，没有复用组件库。不要继续口头提醒，直接写进 AGENTS.md。

规则改成“业务页面不得直接写 button，必须使用 Button 组件；例外需要说明原因”。下一次 Agent 任务前先读取规则，返工明显减少。

进一步落地：从 Review 返工提炼规则

规则不是凭空写出来的。最好的规则来自 Review 返工：AI 连续两次犯同样错误，就把这个错误写成明确规则。比如“不要直接写 button”比“遵守组件规范”更有用。

技能卡模板

技能：新增业务页面
1. 先找相似页面。
2. 列出可复用组件。
3. 实现四态：loading/empty/error/success。
4. 检查 375px 和 1440px。
5. 补 story 或测试。
6. 输出验证命令和风险。

规则文件应该像项目接口

AGENTS.md、Rules、Instructions 不是写给人看的宣言，而是写给 Agent 执行的接口。接口要稳定、明确、可验证。比如“组件要好看”不是接口，“新增卡片组件必须复用 Card、Button、EmptyState，并覆盖 375px 宽度”才是接口。

推荐目录级规则

src/components:
  只放通用组件，不引入业务接口。
src/pages:
  可以组合业务逻辑，但不复制通用 UI。
src/api:
  只封装请求，不处理页面状态。
tests:
  不删除断言；快照变更必须说明原因。

目录级规则能减少误伤。比如 Agent 修一个页面 bug 时，不应该顺手改组件库公共 API；改组件库时，也不应该引入业务接口。把边界写清楚，能让 AI 的改动更像团队成员，而不是外包脚本。

技能化的判断标准

如果某个流程每周都会出现三次以上，就值得写成技能。例如“新增业务页”“修测试失败”“补 Story”“处理接口错误态”“根据设计稿实现组件”。技能里不要塞太多背景知识，重点写步骤和验收。

维护规则的方式

每次 review AI 代码时，把问题分类：缺上下文、改动范围过大、组件 API 猜错、测试没跑、样式不符合规范。如果某类问题出现两次，就把对应规则写进文件。规则要短，能被执行；过长的规则会被忽略，或者让 Agent 把时间花在读文档上。

一个实用底线

让 Agent 在动手前先复述计划。计划里必须包含文件范围、验证命令和风险。你确认后再让它写代码。这个步骤会多花几十秒，但能避免大量“已经写完但方向错了”的返工。

优秀规则文档的写法：短、硬、可验证

别人写 AI 规则经验文时，经常强调“不要写价值观，写操作约束”。例如“保持代码优雅”没有用，因为无法验证；“新增表格必须复用 DataTable，分页逻辑放在 usePagination，不在页面里重复写”才有用。规则越像 lint，Agent 越容易遵守。

AGENTS.md 推荐结构

# 项目概况
框架、包管理器、启动命令。

# 目录边界
哪些目录放页面，哪些放组件，哪些放 API。

# 编码规则
组件、样式、状态、错误处理。

# 测试规则
什么时候补单测、story、e2e。

# 禁止事项
密钥、生产配置、锁文件、未批准依赖。

规则如何迭代

不要一次写几千字规则。先写 20 条最常见约束，然后用真实 PR 验证。每当 AI 犯同一个错误两次，就把规则补一条。每当规则长期没被触发，就删掉或合并。规则文档应该像代码一样维护，不是写完就放着。

技能卡示例：新增页面

触发：用户要求新增业务页面。
步骤：
1. 先找相似页面和路由模式。
2. 列出可复用组件和缺失信息。
3. 实现 loading / empty / error / success。
4. 补 story 或测试。
5. 输出文件列表和验证结果。

技能卡的价值是让团队少说重复话。只要流程稳定，就能让不同人、不同 Agent 都按同一套质量底线交付。
