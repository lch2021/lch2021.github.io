Cursor Background Agents、Rules 与 MCP：把设计、任务和代码连起来

2026年4月29日 下午 2765 字 6 分钟
CursorMCPRules

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

Cursor、Rules、MCP、Background Agents 组合起来很强，但也很容易乱。没有 Rules，Agent 会猜项目约定；MCP 接太多，权限和上下文会失控；后台任务写得开放，产物就会变成大量主观改动。

这篇讲一个更稳的顺序：先写项目规则，再接最少 MCP，再给后台 Agent 明确边界，最后用证据审查远程分支。

核心痛点

  • Cursor 能改代码，但没有 Rules 时会不断猜项目约定。
  • MCP 接太多工具，上下文变复杂，权限也变模糊。
  • Background Agent 任务写得开放，结果生成大量主观改动。
  • 远程分支缺少证据，只给“完成了”的总结。

详细解决方案：Rules 先行，MCP 精简，后台任务可验收

Cursor 类工具的质量取决于上下文质量。先写 Rules，再接 MCP，最后才让 Background Agent 跑任务。否则它只是一个执行很快、但不懂你项目的新人。

Rules 三层结构

  • 全局：框架、包管理器、禁止事项、测试命令。
  • 目录：pages、components、api、tests 的职责边界。
  • 任务：本次 issue 的目标、范围、验收和风险。

MCP 接入优先级

第一批只接最能提升前端质量的工具：Figma 读设计、Storybook 读组件、Playwright 操作浏览器。工单、监控、部署等工具后接，并且要单独做权限控制。

后台任务输出必须包含：
- 修改文件列表
- 运行过的命令
- 未运行命令及原因
- 截图或测试证据
- 需要人工确认的风险

实战案例：设置页空状态后台实现

先在 Rules 里写清组件复用和禁止事项，再让 Background Agent 查询 Storybook 中的 EmptyState、Button、Card 用法。

Agent 提交分支后必须附带文件列表、Storybook 预览路径和测试命令。没有证据的远程分支不进入 Review。

进一步落地：先写规则，再交给后台 Agent

Background Agent 适合处理耗时任务，但它不应该替你决定产品方向。把任务交出去前，先写规则：组件怎么复用，哪些目录不能碰，哪些工具可以用，失败时如何回报。

Rules 示例

# 前端 UI 规则
业务页面不得直接写 button/input/modal，必须复用组件库。
新增页面必须覆盖 loading、empty、error、success。
移动端 375px 不允许横向滚动。
不确定组件 props 时，先查 Storybook MCP。

# Background Agent 限制
不修改 package.json 和 lockfile。
不修改部署配置。
不访问生产环境。
PR 描述必须包含测试结果。

MCP 接入策略

最少接入原则：先接 Storybook 和 Figma，因为它们直接影响 UI 质量；再接 Playwright，因为它能验证真实交互；最后再考虑工单、监控和部署。每多接一个 MCP，就多一层权限和数据边界。

后台任务验收

后台分支必须给证据：截图、测试命令、失败说明、未覆盖风险。没有证据的“已完成”不能进入 Review。

Rules 是 Cursor 提效的地基

如果没有 Rules，Background Agent 只能靠当次 prompt 猜项目习惯。前端项目的习惯又特别多：组件库怎么用，样式写在哪，接口层怎么封装，图标从哪里引入，哪些目录不能碰。把这些写成项目规则，Agent 才能像一个认真读过 onboarding 文档的新同事。

一个前端 Rules 示例

所有页面组件放在 src/pages。
共享 UI 放在 src/components，不要在页面中复制组件代码。
样式优先使用 CSS variables 和 design tokens。
新增表单必须覆盖校验错误、提交中、提交失败状态。
任何涉及路由和权限的变更必须说明影响面。

MCP 连接什么最有价值

前端最值得接的 MCP 通常是 Figma、Storybook、浏览器自动化和文档。Figma 解决设计上下文，Storybook 解决组件 API，Playwright/浏览器解决真实交互，官方文档解决 API 版本。不要为了“看起来先进”连接一堆工具，工具越多，权限和数据边界越复杂。

Background Agent 的任务边界

它适合跑比较久的任务，但不适合开放式探索。你可以让它“给设置页补三种状态并添加 story”，不要让它“优化设置页体验”。前者能验证，后者会产生大量主观改动。对于后台 Agent，最关键的提示词是“不确定先问，不要自行扩大范围”。

审查远程分支

远程 Agent 可能会自动 commit 或推分支。审查时先看是否新增了依赖、是否修改了锁文件、是否触碰了配置和脚本。再看 UI 是否使用了已有组件。最后运行本地验证，因为远程环境通过不等于你的开发环境和部署环境都通过。

Cursor 类文章常见结构：先搭环境，再写规则，再做任务

高质量 Cursor 教程通常不会一开始就展示炫酷生成效果，而是先讲设置和规则。原因很简单：如果仓库索引、Rules、MCP、测试命令都没准备好，Agent 只能靠猜。前端项目的“猜”成本很高，最后会变成你手动收拾一堆不符合规范的代码。

Rules 的三层写法

  • 全局层：语言、框架、包管理器、禁止事项。
  • 目录层：pages、components、api、tests 各自能做什么。
  • 任务层：当前 issue 的目标、范围和验收。
全局：项目使用 TypeScript，禁止 any 扩散。
目录：src/components 不引入业务 API。
任务：本次只修改用户设置页，不改全局导航。

MCP 不要一次接太多

MCP 的价值是补上下文，不是堆功能。对前端来说，第一批只接三类就够：Figma 读设计，Storybook 读组件，Playwright 操作浏览器。等团队确认权限和日志没问题，再考虑接工单、监控、文档和部署。

Background Agent 的验收方式

远程 Agent 交付后，要求它写出“我修改了什么、为什么这么改、跑了哪些命令、哪些没跑、还剩什么风险”。如果 PR 描述只有泛泛总结，说明它没有形成可审查交付。你要的是工程证据，不是漂亮描述。
