Claude Code技能终端

这篇文章基于 2026-04-29 可公开访问的官方资料整理，面向前端工程师的日常提效场景。

终端 Agent 的优势不在聊天，而在“贴近现场”：它能读日志、跑测试、看 diff、改文件。真正的问题是，很多人把错误日志扔给它后直接让它修，结果它可能删断言、改快照、绕过真实问题。

这篇把 Claude Code 这类终端 Agent 当作故障处理器来设计：先定位，再假设，再最小修复，再复跑测试，最后把流程沉淀成技能卡。

核心痛点

  • 终端报错很多，开发者把完整日志丢给 AI 后得到泛泛建议。
  • Agent 直接改测试，让红灯变绿但问题没有修。
  • 重复流程没有沉淀，每次修测试都重新解释项目规则。
  • 命令权限不清晰，安装依赖、改锁文件、部署容易失控。

详细解决方案：把终端 Agent 用成故障处理器

Claude Code 这类终端 Agent 的强项是读取日志、定位文件、运行命令。不要让它一上来“帮我修好”，而要让它按排障流程工作：先定位、再假设、再最小修复、最后复跑。

测试失败技能卡

触发：Vitest/Playwright/Storybook 报错。
步骤：
1. 读取完整报错和失败用例。
2. 找最近相关 diff，不直接改测试。
3. 输出根因假设和候选文件。
4. 做最小实现改动。
5. 先跑单个测试，再跑相关套件。
禁止：删除断言、扩大快照、无确认改锁文件。

权限边界

允许自动执行只读命令和测试命令；安装依赖、修改锁文件、删除文件、执行部署必须人工确认。终端 Agent 能力越强，越要把命令边界写清楚。

实战案例：Vitest 快照失败处理

测试失败后不让 Agent 直接更新快照，而是先定位组件 props 变化和最近 diff。确认是样式 token 改动后，再更新实现而不是放宽断言。

最终只改组件样式映射和一条明确断言，快照没有被无脑扩大。这个流程可以沉淀成“修测试失败”技能。

进一步落地：把一次排错变成技能

终端 Agent 最有价值的场景不是生成新功能，而是处理失败现场。比如 Vitest 报错、Playwright 超时、构建失败、类型爆红。每次排错都应该沉淀为技能：输入是什么、先读什么、禁止做什么、如何验证。

技能卡：修复 Playwright 超时

触发：Playwright 测试 timeout。
步骤：
1. 读取失败用例和 trace。
2. 判断是选择器不稳定、接口未 mock、动画等待还是真实 bug。
3. 不允许直接把 timeout 调大。
4. 优先修等待条件或业务状态。
5. 复跑单个用例，再跑同目录用例。

命令权限分级

命令是否可自动执行
rg、sed、git diff、npm test 单用例可以
npm install、改 lockfile需要确认
部署、删除文件、清空缓存禁止自动执行

质量要求

修复完成后，Agent 必须说明：根因是什么、为什么这样改、改了哪些文件、跑了哪些命令、哪些命令没跑。没有这些信息，不能算完成。

终端 Agent 适合做什么

Claude Code 这类终端 Agent 的优势是离工程现场很近。它能看到脚本、日志、测试输出、Git diff，也能在修改后马上运行命令。前端项目里，终端上下文往往比单纯聊天更重要，因为很多问题只有在构建、测试、浏览器截图或 CI 日志里才暴露。

把技能写成流程，而不是知识点

一个好技能应该回答四个问题：触发条件是什么，先读什么文件，允许改什么范围，如何验证完成。比如“修复样式回归”技能不能只写“注意响应式”，要写“先打开对应 story，再截图 375、768、1440 三个宽度，比较按钮、间距和换行”。

技能：修复样式回归
触发：截图、视觉测试、QA 反馈中出现布局异常。
读取：相关组件、story、设计 token、最近 diff。
限制：优先改局部样式，不改全局 reset。
验证：运行 story 测试，至少检查移动端和桌面端。

Subagent 分工示例

对于稍大的任务，可以让不同 subagent 承担不同视角：一个只看类型和测试，一个只看 UI 状态和 a11y，一个只看依赖和安全。这样比让一个 Agent 同时兼顾所有问题更稳。最后由主 Agent 或人类整合结论，避免多个子任务互相覆盖。

Hooks 的实际价值

Hooks 适合做团队底线，比如写文件前检查是否修改了锁文件、提交前提醒运行 lint、会话开始时自动加载 AGENTS.md。它不是为了制造复杂自动化，而是为了减少“每次都忘记说明”的环节。

落地建议

先给团队准备 3 个技能：修测试、补 Story、查生产报错。每个技能只服务一个明确场景。用两周时间观察哪些步骤经常返工，再把规则收紧。技能库不是越多越好，真正有用的是那些能稳定减少返工的流程。

终端文章的好写法：从一次失败日志开始

我看到不少实用型文章都会从一个具体报错切入，而不是先介绍工具功能。Claude Code 这类终端 Agent 最适合这样写：先贴出测试失败或构建失败，再展示如何让 Agent 读日志、定位文件、做最小修复、重新运行命令。读者能直接把流程搬到自己的项目。

测试失败处理流程

1. 粘贴完整错误，不要只写“测试挂了”。
2. 让 Agent 找到失败用例和最近相关改动。
3. 要求它复述根因假设，不允许先删断言。
4. 只修一个失败点，重新运行单个测试。
5. 单测通过后再跑相关测试套件。

这个流程的重点是“先解释，再修改”。很多 Agent 会倾向于直接改测试，因为这是最快变绿的方法。前端项目里尤其要警惕快照测试，AI 可能把真实视觉回归变成一次无意义的 snapshot update。

技能库怎么命名

技能名称要按场景命名，而不是按工具命名。比如“修复 Vitest 失败”“补 Storybook 状态”“根据 Figma 实现组件”“排查线上白屏”。这样团队成员在需要时能直接调用，不需要知道背后用了哪个模型。

终端 Agent 的边界

  • 允许它运行只读命令和测试命令。
  • 安装依赖、改锁文件、执行部署前必须确认。
  • 涉及环境变量、密钥、生产地址时只分析不输出敏感值。
  • 每次修改后必须给出文件列表和命令结果。

终端 Agent 的优势是贴近真实工程环境，但这也是风险来源。它越能跑命令，越需要明确哪些命令可以自动执行，哪些必须停下来问。
