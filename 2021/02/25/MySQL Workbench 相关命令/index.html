MySQL Workbench 常用 SQL 命令整理

2021-02-25 1888 字 4 分钟

SQL 学习重点

SQL 不只是记命令，更重要的是理解数据表、字段、条件和结果集之间的关系。Workbench 只是图形化工具，核心仍然是 SQL。

基础查询

select * from users;
select id, username, status from users;

生产环境不要随意 select *，字段过多会增加网络和解析成本，也容易暴露不该返回的数据。

条件查询

select * from users where id = 5;
select * from users where status = 1 and age >= 18;
select * from users where username like '%tom%';

and 表示同时满足，or 表示满足任意条件。复杂条件建议加括号，避免优先级导致结果不符合预期。

新增、修改、删除

insert into users (username, password) values ('tom', '123456');
update users set status = 0 where id = 5;
delete from users where id = 5;

update 和 delete 必须带 where。执行前可以先用 select 检查目标数据，避免误改全表。

排序和分页

select * from users order by id desc;
select * from users order by created_at desc limit 10 offset 20;

分页常用于列表接口。大数据量分页要注意性能，后期可以考虑基于 id 或时间的游标分页。

聚合统计

select count(*) from users;
select status, count(*) from users group by status;
select max(age), min(age), avg(age) from users;

常见错误

  • from 写成 ftom。
  • 字符串忘记加引号。
  • update/delete 忘记 where。
  • order by asc/desc 含义混淆：asc 升序，desc 降序。
  • 字段名和关键字冲突时需要反引号。

实践建议

写 SQL 时先写 select 验证结果，再写 update/delete。重要操作开启事务，确认无误后 commit，出错 rollback。

常见痛点

  • update/delete 忘记 where：学习阶段最容易出现的高风险操作。
  • 只会 select *：字段越多越慢，也容易把密码、token 等敏感字段查出来。
  • 分页越往后越慢：大 offset 会扫描并丢弃大量数据。
  • 不知道事务怎么兜底：多条相关写操作中途失败后，数据可能半成功半失败。

SQL 编写流程

Step 1先确认目标数据
→
命令select 字段 from 表 where 条件
Step 2是否是写操作？
→
是开启事务并确认 where
→
否关注索引、排序和分页
Step 3执行后复核
→
命令select 再查一次，必要时 commit / rollback

详细解决方案

Workbench 里做重要修改时，可以先开启事务。先 select 确认影响范围，再 update 或 delete，最后复查结果。确认无误后 commit，发现问题就 rollback。

start transaction;
select id, status from users where id = 5;
update users set status = 0 where id = 5;
select id, status from users where id = 5;
commit;

分页查询前期可以用 limit offset，数据量变大后要考虑游标分页。例如按 id 从上一次最后一条继续查，避免很大的 offset。

select id, username
from users
where id > 1000
order by id asc
limit 20;

排查清单

  • 查询很慢，先 explain 查看是否走索引。
  • 结果数量不对，检查 and/or 优先级并加括号。
  • 中文乱码，检查表、字段、连接字符集是否一致。
  • 误操作后不要继续写入，优先确认是否有事务、备份或 binlog 可恢复。
