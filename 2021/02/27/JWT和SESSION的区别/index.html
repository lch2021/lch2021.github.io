JWT 和 Session 的区别：认证方案怎么选

2021-02-27 1886 字 4 分钟

认证要解决什么问题

HTTP 是无状态协议。用户登录后，服务端需要知道后续请求来自谁。Session 和 JWT 都是在解决“如何识别用户身份”的问题，但思路不同。

Session 的工作方式

Session 通常由服务端保存用户状态，浏览器保存一个 session id。请求时浏览器带上 session id，服务端查 session 数据。

  • 优点：服务端可控，退出登录和踢下线容易。
  • 缺点：分布式部署需要共享 session，例如 Redis。

JWT 的工作方式

JWT 是签名后的 token，服务端签发后交给客户端保存。请求时客户端带上 token，服务端验证签名并读取 payload。

Authorization: Bearer <token>
  • 优点：无状态，适合前后端分离和多服务调用。
  • 缺点：签发后在过期前不容易主动失效。

核心区别

维度SessionJWT
状态存储服务端客户端保存 token
扩展性需要共享存储天然无状态
主动失效容易需要黑名单或短过期
数据大小cookie 较小token 可能较大

安全注意事项

  • JWT payload 不要放敏感信息，它只是编码，不是加密。
  • 使用 HTTPS，避免 token 被中间人截获。
  • token 过期时间不要过长，可以使用 refresh token。
  • Session cookie 建议设置 httpOnly、secure、sameSite。

怎么选

传统服务端渲染、强控制登录状态、需要随时踢下线，Session 更合适。前后端分离、多端登录、微服务调用，JWT 更常见。实际项目也可以组合使用：短期 access token + 可控 refresh token。

常见痛点

  • 只看“无状态”就选 JWT：忽略了退出登录、踢下线、权限即时变更这些需求。
  • 把敏感信息放进 token：JWT payload 只是编码，不等于加密。
  • Session 分布式问题没设计：多台服务实例下，如果没有共享存储，用户状态会不稳定。
  • token 过期策略混乱：access token 太长不安全，太短又影响体验。

详细解决方案

如果选择 JWT，推荐拆成短期 access token 和长期 refresh token。access token 用于访问接口，过期时间短；refresh token 用于换新 token，可以保存在更安全的位置，并在服务端记录状态。

登录成功
  - 返回 accessToken：15 分钟
  - 返回 refreshToken：7 天
访问接口
  - accessToken 有效：正常返回
  - accessToken 过期：使用 refreshToken 换新
退出登录
  - 删除 refreshToken 记录或加入失效列表

如果选择 Session，生产环境要把 session 存到 Redis 这类共享存储里，并设置 cookie 的 httpOnly、secure、sameSite。这样即使服务横向扩容，请求落到不同实例也能识别用户。

排查清单

  • 用户退出后仍能访问，检查 token 是否还有效以及后端是否做了黑名单或 refresh token 失效。
  • 多实例登录状态丢失，检查 Session 是否使用共享存储。
  • 接口偶发 401，检查客户端刷新 token 是否存在并发覆盖问题。
  • 前端拿不到 cookie，检查 sameSite、secure、domain 和跨域 credentials。
