流式回答的演示往往只有几行代码：发起请求，收到一段文本，就把它追加到页面上。真正落到多端应用，问题会立刻变成另一种形状：小程序收到的是二进制分块，浏览器读的是 ReadableStream，旧容器可能只能通过 XHR 观察不断增长的 responseText；用户关闭弹层后，网络回调却仍可能抵达；服务端已经结束，打字机动画还没有播放完。

这篇文章来自一套多端应用的匿名化工程实践。所有接口、业务名、标识符和示例数据都已替换。讨论的核心不是某个框架的 API，而是一个更通用的问题：如何把不稳定到达的字节流，转换成可验证、可取消、不会串到下一次会话的界面状态。

一、先把“流”拆成五层

排查流式问题时，最容易犯的错误是直接盯着页面上的文字。页面是最后一层；前面任一层出错，都可能表现成“少字”“乱码”“重复”“一直转圈”。我把链路拆成五层：

层次输入与输出典型故障
传输HTTP 响应 → 二进制块或增量文本平台不支持、请求被缓存、取消失效
解码字节块 → 连续的 UTF-8 文本汉字跨块后出现替换字符
协议文本流 → 完整 SSE 事件半条事件被提前消费、CRLF 解析失败
会话事件 → 当前请求的状态变更旧请求回写新页面、结束与取消重复触发
呈现待显示文本 → 可见文字逐字动画积压、滚动抖动、完成态过早出现

这张表也给出了排错顺序：先检查网络是否真的分块，再看解码后的文本，再看事件边界，最后才看组件渲染。否则很容易用一个 UI 补丁掩盖协议层的问题。

二、平台分叉只留在传输层

同一份业务代码运行在浏览器、小程序和内嵌 WebView 时，不能假设它们都以同一种方式提供增量响应。工程里采用了三条接收路径：小程序请求任务开启分块并监听块回调；现代 H5 使用 fetch 读取 response.body；兼容路径使用 XHR，根据上次读取位置取出新增长的文本。

平台适配器
  ├─ 小程序：request({ enableChunked: true }) → ArrayBuffer
  ├─ H5：fetch() → ReadableStream<Uint8Array>
  └─ 兼容 H5：XHR responseText → 新增的字符串片段
                         ↓
                 统一的协议解析器
                         ↓
                 统一的会话状态机

关键在于接口边界：适配器只负责“产生增量内容”和“中止请求”，不理解业务事件，也不直接修改页面。GET 参数拼接、POST 请求体、请求头、超时和取消都在适配器内完成。这样同一种 SSE 帧只需解析一次，页面也不必知道它来自哪一种容器。

这里还有一个常被忽略的细节：浏览器原生 EventSource 的使用模型与带自定义请求体的 POST 流不同。若接口要求 POST、认证头或特殊参数，就不能把原生 EventSource 当作现成的替换品；使用 fetch 读取事件流时，断线重连和 retry 语义也要由应用自己设计。

三、传输块不是字符边界，更不是事件边界

假设服务端发出 data: 你好\n\n。一个三字节 UTF-8 汉字可能被拆在两个网络块之间，甚至 \n\n 也可能被拆开。因此下面两种写法都不可靠：

// 错误一：每个块都创建新解码器，跨块汉字会损坏
const text = new TextDecoder().decode(chunk);

// 错误二：把一个块当成一个完整事件
onMessage(text.slice(6));

正确的顺序是每条连接保留一个解码器，再保留一个未完成文本缓冲区。解码器负责跨字节块拼好字符；协议缓冲区负责跨文本块拼好事件。二者处理的边界不同，不能合并成一个“字符串追加”步骤。

const decoder = new TextDecoder('utf-8');
let pending = '';

function receiveBytes(bytes) {
  pending += decoder.decode(bytes, { stream: true });
  drainCompleteFrames();
}

function endBytes() {
  pending += decoder.decode(); // 冲洗解码器里剩余的字节
  drainCompleteFrames();
  // 不把未以空行结束的半条事件当成完整事件发布
}

小程序端尤其要注意：若每次 onChunkReceived 都独立解码一个 ArrayBuffer，只要汉字恰好跨块，就可能出现 �。实际工程里已经有分块接收和文本缓冲的骨架；把解码器提升为“单次连接级别”的状态，是进一步加固中文内容完整性的关键。

四、SSE 解析要按“行”和“空行”工作

SSE 是文本协议，而非“每块一段 JSON”。一条事件可以有 event:、id:、多行 data: 和 retry:；空行才表示事件结束。协议允许 LF、CRLF 或 CR 作为行尾，冒号开头的行是注释。只按 \n\n 切分，可以覆盖受控服务端的一部分输出，却不能覆盖所有合法帧。

: keep-alive
event: delta
id: 17
data: 第一行
data: 第二行

event: complete
data: {"ok":true}

解析器应当增量读取“完整的行”，在空行处派发事件。连续的 data: 行按换行拼接；没有 data: 的心跳或注释不应成为内容消息；服务端给出的 retry: 只是建议重连间隔，不会让自定义 fetch 客户端自动重连。若业务还约定 [DONE] 之类结束标记，应把它明确标为应用层约定，不要误认为 SSE 标准字段。

解析器的输出最好是结构化事件，例如 { type, data, id }。页面消费 delta、error、complete 等语义，不接触原始字符串。这样服务端增加心跳或统计事件时，不会把它们误加到回答内容里。

五、真正难的是“当前请求”这件事

传输能跑通后，最隐蔽的错误通常来自异步时序。用户可能连续点击生成、关闭再打开弹层、切换消息、离开页面，或在网络超时后重试。旧请求的回调到达时，组件实例可能还活着，但显示的已经是另一条内容。只靠一个布尔值 loading 无法证明回调属于当前会话。

工程里已经能看到两道重要防线：发起请求前做重复请求拦截；关闭弹层时中止流，并在消息回调里检查可见状态。进一步稳妥的做法，是给每次请求分配单调递增的代号，并让所有回调先验证代号：

let generation = 0;
let activeTransport = null;

function start() {
  activeTransport?.abort();
  const mine = ++generation;
  activeTransport = openStream({
    onEvent(event) {
      if (mine !== generation) return;
      applyEvent(event);
    },
    onError(error) {
      if (mine !== generation) return;
      finish('failed', error);
    },
  });
}

function close() {
  ++generation;           // 先使旧回调失效
  activeTransport?.abort();
  activeTransport = null;
}

“先使旧回调失效，再取消请求”是顺序上的小细节。取消本身也可能触发错误回调；先换代号，旧回调即使迟到也不能写入新状态。sessionId、消息 ID 或请求代号应当有清晰职责：服务端会话标识用于续传和排查，本地代号用于隔离组件里的异步回调，二者不应混用。

六、把结束、失败、取消做成互斥终态

流式请求至少有 idle → connecting → streaming，终态则分为 completed、failed、cancelled。三种终态不能都走同一个“完成”回调：用户主动关闭不应显示“生成失败”；HTTP 非 2xx 不能被当成正常结束；服务端 error 事件也不能因为连接随后关闭而被覆盖成成功。

触发应进入的终态页面动作
业务完成事件或明确的结束标记completed保存完整结果，等待呈现队列清空
HTTP 错误、超时、协议错误failed保留已收到内容，给出可重试状态
用户关闭、切换对象、离开页面cancelled中止网络和动画，忽略迟到回调
没有明确完成语义的意外断流failed 或待恢复按服务端契约决定是否可续传

状态迁移集中在一个 finish(reason) 函数里，可以确保计时器、请求句柄和防重复标记只清理一次。重试前还要回答一个协议问题：服务端是否支持按事件 ID 或业务游标续传？如果不支持，自动重连可能把已经显示的内容再追加一遍。此时“允许用户手动重试”比盲目自动重连更可靠。

七、接收速度和显示速度要解耦

流式数据到达的节奏由网络和服务端决定，打字机效果的节奏由界面决定。一个实用做法是：网络回调只把文本追加到 pendingText；单独的计时器从队列中取字符更新可见文本。这样一次到达很大的片段，页面也不会瞬间跳到末尾。

但解耦后会出现新的结束条件：网络完成 ≠ 用户已经看完。网络已经收完时，队列里可能还有几百个字符。若立即把按钮恢复、缓存最终文本或隐藏加载态，界面会出现“已完成但还在打字”的矛盾。更清楚的状态是 streaming → draining → completed：传输结束进入 draining，队列清空后才进入视觉完成态。

还要设置积压策略。若队列增长速度长期高于播放速度，就应动态加快每次消费量，或者在用户滚动到历史消息、关闭弹层时直接一次性冲洗剩余文本。否则一段 2000 字的回答按每 100 毫秒一个字播放，需要 200 秒，网络早已结束，体验却像系统卡住。

八、用切块测试验证，而不是只用顺畅网络验证

最有价值的测试不是“输入一句话后出现文字”，而是把同一份字节流以不同边界喂给解析器，观察输出是否一致。下面这组用例足以暴露多数隐藏问题：

  1. 把一个汉字的三个 UTF-8 字节拆成三个块，结果仍应是原字。
  2. 把 \r\n\r\n 拆在四个块中，事件只派发一次。
  3. 把 data: 字段名拆开，再把多行 data: 拼成一条事件。
  4. 注释行、空数据、未知事件类型不会混入可见回答。
  5. 请求 A 结束前启动请求 B，A 的迟到回调不能修改 B。
  6. 用户主动取消后，不触发成功、失败提示或重复扣减动作。
  7. 模拟 HTTP 错误、超时、正常结束和意外断流，终态各不相同。

可以做一个确定性的“所有切分点”测试：给定一条短 SSE 样本，在每个字节位置切成两段分别输入；再覆盖若干三段切法。断言每次得到完全相同的事件序列。它不依赖真实网络，运行快，却正好验证流式处理最薄弱的边界。

九、观测指标也要围绕这五层设计

排查线上问题时，不宜记录原始回答、令牌或完整请求体。更有用的是非敏感指标：连接建立耗时、首个字节耗时、首个完整事件耗时、接收块数量、解码错误次数、事件数量、队列最大长度、取消原因、终态及耗时。用本地请求代号关联一次交互内部的日志即可，避免把用户内容当作排查材料。

例如“文字迟迟不出现”可以由三个时间点定位：请求很快建连，但首字节慢，说明服务端或代理没有及时输出；字节到了而完整事件迟迟没有，说明帧没有及时以空行结束；事件到了而可见文字慢，说明是打字机队列或渲染频率问题。每一层都能给出不同的修复方向。

十、这次实践留下的工程判断

流式交互真正需要守住的不是“尽快把字符放到屏幕上”，而是四个不变量：一个字节不丢，一个事件不重，一个旧请求不串，一个终态只发生一次。围绕这四点组织代码，平台差异才能被收在传输层，协议解析才能被独立测试，页面也才能放心处理打字、滚动和重试。

现有工程实践提供了跨端传输、事件缓冲、请求取消和显示队列的完整观察样本。本文进一步提出的连接级 UTF-8 解码、完整行解析、代号隔离和终态状态机，是基于这些边界整理出的加固方案；它们是可复用的设计方法，不表示原工程已经逐项实现。以后再遇到“偶发乱码”“关了弹层还更新”“结束后一直转圈”，从五层链路定位，通常比继续给页面加布尔值更快找到根因。
